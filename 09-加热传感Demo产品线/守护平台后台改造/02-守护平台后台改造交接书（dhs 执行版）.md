# 织序智慧感知守护平台 · 后台改造交接书（dhs 执行版）

> **这份文档怎么用**：dhs 拿它 + 旧后台代码，按「§4 信息架构 → §5 映射 → §6 页面改动 → §7 数据模型 → §8 接口」从上到下改。UI 见配套 `03-云平台 UI 设计大纲（范围）`。
> **交付目标**：把旧「智慧养老看护系统」后台，改造为「**织序智慧感知守护平台**」后台（Web 端）。
> **本轮范围**：**只做 Web 后台**；小程序下一步。不改设备协议（沿用 `设备通信协议与数据规范 v1.0`）。

---

## 0. TL;DR（给 dhs 的 6 条铁律）

1. **只泛化、不重写**：老后台的页面骨架、图表、表格都复用，做「泛化 + 新增」，别推倒重来。
2. **术语要统一**：`老人`→`守护对象`、`告警`→`预警/风险`、`报警`→`提醒`。**禁用**「报警/监护/诊断」。
3. **心率/呼吸/体重一律是"估计/趋势·非医疗"**，且**可隐藏**——不准就不显示，但**保留 UI 位置与开关**。
4. **物业是"轻集成"**：不做工单派发；物业不登录、不操作；靠微信/短信收告警。
5. **位置 = 首次台账登记**（项目→小区→楼栋→单元→楼层→房号→设备），**不是实时定位**；换手走小程序换绑、后台留变更记录。
6. **UI 要好看**：简洁清爽、银白卡片、大卡+小卡主次层次（详见 `03-UI 大纲`）。

## 1. 背景与目标

- **平台名**：织序智慧感知守护平台（原"智慧养老看护系统"，去"养老"锁定）。
- **战略目的**：先用**自有物业/楼盘**跑出**真实数据与规模**，支撑对外售卖与融资；因此后台要「**真实、全面、好看**」。
- **业务**：压力床垫 / 宠物垫 → 云端 → 后台（+小程序）。覆盖 **养老 / 宠物 / 场景包**。
- **本轮**：Web 后台改造（含数据看板、告警中心、设备管理、守护对象、物业轻模块、售后、数据分析、系统管理）。

## 6. 页面级改动清单

> 每页给：目的 / 主要区块 / 关键控件 / 数据来源。

### 6.1 数据看板（新增/重构）
- **运营态势**：KPI 卡行（在线设备/在床/告警中/待处理/在线率/平均响应时长）；实时告警列表；故障设备；Top 风险。
- **经营增长**（Tab/折叠）：设备增长曲线；覆盖（项目/小区/楼栋/楼层比例）；服务人数；付费床位（预留）。
- **设备分布地图**：层级下钻（项目→小区→楼栋→单元→楼层→房号→设备）；覆盖热力。
- 数据来源：`devices/device_status/alerts/stats_*`。

### 6.2 告警中心（升级）
- 实时告警（L1/L2/L3 分级着色）；筛选（类型/级别/项目/状态）。
- 处置：接单→处理→归档；处理人/备注/照片；升级链。
- 响应策略：**家属优先；家属不在 → 联系物业上门**。免打扰/静默（含审计）。
- 数据来源：`alerts/alert_rules`。

### 6.3 设备管理（泛化 + 新增）
- 台账（列表 + 筛选 + 导入/导出）。
- 类别（床垫/宠物垫）；型号（参数/固件）。
- 绑定/解绑（绑定守护对象 + 归属房号）；**变更记录**。
- 详情（实时状态/压力分布/热力图/实时压力）。
- **预警设置**（生效时段 + 阈值；三级配置）。
- **功能开关**（按类别显示可开功能；心率默认隐藏）。
- OTA/远程诊断。

### 6.4 守护对象管理（泛化）
- 档案（类型=老人/宠物；标签；同意状态）。
- 标签/分组；绑定关系；关系人（家属/亲友/紧急联系人 + 通知顺位）；归属（房号）；服务/场景包。

### 6.5 物业管理（新增·轻）
- 组织：项目→小区→楼栋→单元→楼层→房号（CRUD）。
- 公告/资讯：发布/编辑/删除/推送。
- 人群标签：标签/分组。
- 服务/安全报告：**自动生成**月报（只读）。

### 6.6 售后管理（新增·我方）
- 售后工单（报修/维修/换货/记录）+ 处理流转 + 关联设备。
- 转达记录（物业/用户转达）。

### 6.7 数据分析（扩展）
- 报表（设备/床位/项目/时间 + 指标）；告警记录历史；导出（xlsx/csv/pdf）；对账。

### 6.8 系统管理（新增/扩展）
- 账号与权限（RBAC）；租户/组织（强隔离）；通知模板与通道；全局开关；数据字典；操作日志/审计；数据留存与合规。

## 11. 技术架构选型（2026-10-10 更新）

### 11.1 现状（旧后台依赖，已确认）

```
fastapi==0.104.1 · uvicorn[standard]==0.24.0 · pydantic==2.5.0
numpy==1.24.3 · pyserial==3.5 · python-multipart==0.0.6 · starlette==0.27.0
```

→ 结论：后端 = **Python + FastAPI**（现代异步 API 框架）。

> ⚠️ **两个重要发现**：
> 1. **当前没有数据库依赖**（无 `SQLAlchemy`、无 MySQL 驱动）→ **本轮"加数据库"是核心新增工作**。
> 2. **依赖含 `pyserial`** → 现在这个 FastAPI 后端**还兼着"读串口"（PC 网关）的活**，采集与后台耦合。**建议解耦**：将来设备走 WiFi/IoT 平台，业务后台不该管串口（见《功能需求 v1.1》架构）。

### 11.2 决策：**保留 Python / FastAPI，不换 Java（Spring Boot）**

针对"旧后端是 Python + 单人开发 + 基本靠 AI(dhs) 写 + 不熟 Java"：**不重构为 Spring Boot**。
理由：换 Java = 后端**重写**（非改造）+ 运维更重（JVM）+ 更难把关；而"脚手架红利"在 AI 写代码时并不成立。
→ **FastAPI + Vue3 前后端分离 = 最优解**。

### 11.3 目标架构

```
[Vue3 前端 SPA] ── HTTPS/JSON ──▶ [FastAPI 业务后端] ── SQLAlchemy ──▶ [MySQL]
                                        │
                                        ├── Redis（缓存 / 队列，可选）
                                        ├── APScheduler（定时：报表聚合 / 离线判定）
                                        └── httpx（对接 IoT 平台 / 短信网关）
```

### 11.4 技术栈清单

| 层 | 选型 | 动作 |
|---|---|---|
| 后端框架 | **FastAPI** | 保留 |
| ASGI | uvicorn | 保留 |
| 校验 | pydantic v2 | 保留 |
| **数据库** | **MySQL 8** | 🆕 新增 |
| ORM / 迁移 | **SQLAlchemy 2.0 + Alembic** | 🆕 新增 |
| 驱动 | PyMySQL | 🆕 新增 |
| 缓存 / 队列 | Redis（可选） | 🆕 新增 |
| 鉴权 | JWT（PyJWT + passlib[bcrypt]） | 🆕 新增 |
| 定时任务 | APScheduler | 🆕 新增 |
| 配置 | pydantic-settings（.env） | 🆕 新增 |
| HTTP 客户端 | httpx | 🆕 新增 |
| **前端** | **Vue3 + Vite + Naive UI + ECharts + Axios + Pinia** | 🆕 重建 |
| 部署 | **Docker Compose**（api + mysql + redis + nginx） | 🆕 |

### 11.5 新增依赖（追加进 requirements，供 dhs 参考）

```
sqlalchemy>=2.0
alembic>=1.13
pymysql>=1.1
redis>=5.0
pyjwt>=2.8
passlib[bcrypt]>=1.7
apscheduler>=3.10
pydantic-settings>=2.0
httpx>=0.27
```

### 11.6 原则（含"不做什么"）

- **单体 + 前后端分离**，**不上微服务 / K8s**。
- **不要用 FastAPI 直接渲染 HTML**（老做法）→ 前端全部走 Vue3 SPA。
- **采集 / 网关与业务后台解耦**（`pyserial` 那部分不混进业务 API）。
- 图表统一 **ECharts**；组件统一 **Naive UI**；主题用 `themeOverrides` 定制"银白 / 卡片式"（见 `03`）。
- 多角色 / 多租户：权限在 **API 层 + 字段级**落实。
- **真实数据优先**：看板数字**可下钻**到设备 / 事件。
